# 10_菜单事件绑定设计 — 引擎评审

- 结论：**有条件通过（引擎无需新增 API；实现前请补 B1~B6 说明）**

## 1. 引擎事实核验

- `menus[].items[].events.onClick` **已支持**：`src/LayoutParser.cpp` 的 `populateMenuPanel` 在创建每个 MenuItem 后调用 `parseEvents(item, itemJson)`；`parseEvents` 的 MenuItem 分支绑定 `kEventClick`（约 3515 行）。
- 菜单项**不要求 id**：事件解析用 `itemJson.value("id", "")` 仅用于诊断；无 id 不阻止绑定。
- 顶层菜单节点不解析事件；separator 在 `populateMenuPanel` 直接 `continue`，不会被绑定；子菜单递归解析。与设计 §4.1/§7 一致。
- 事件 handler 通过 `registerHandler`/`LayoutParser` 的 `m_handlers` 查找；未注册时只记 `handler not registered` 诊断，不影响布局加载。设计要求的“宿主先 `RegisterAction`”成立。
- `docs/schema/declarative-ui.schema.json` 的 `menus.items` 为宽松对象，`events` 当前不会被拒绝；`validate_layout --strict layouts/test_layout.json` 通过。`docs/controls/menu.html` 与 declarative-syntax 已有菜单项 `events.onClick` 示例。
- 现有 `layouts/test_layout.json` 已含菜单项 `events.onClick`，`test_layout` 注册了对应菜单 handler；引擎侧不需要新增菜单事件 API。

## 2. 需补/修订项

### B1. 路径索引必须明确包含 separator

§4.2 的 `menu:<menuIndex>/<itemIndex>` 目前未说明 `itemIndex` 是否计入 separator。建议明确使用 **`menus[i].items` 的原始数组下标（separator 也计数）**；否则插入/删除 separator 会让后续绑定路径整体漂移，§6.2 的“同路径保留”失效。建议在路径说明中写死，并补 separator 前后插入的回归。

### B2. `EventBinding` 需要路径字段

§6.4 要求 event_list/report 使用“菜单/子菜单/...”路径，但当前设计器的 `EventBinding` 只有 `controlId/jsonEvent/handler`（`include/Designer/CanvasPane.h`）。同一 `menu-bar` 的多个菜单项会导出为相同 `control`+`event` 的三元组，无法区分。实现前请扩展 `EventBinding`（增加 `path`/`menuPath`）或明确将路径编码进 `controlId`；并同步 `event_list.json` 的消费方/测试。该修改属于设计器内部，不是引擎 API。

### B3. 唯一性校验与“更新”语义

`CanvasPane::isHandlerNameUnique` 当前只扫描 `m_items[].events`；设计需要扩展到菜单树，且“重复绑定=更新”必须在校验时**排除当前菜单项旧 handler**，否则把同一项从 `A` 改成 `A`（或删除后重加）会被全局唯一检查拒绝。建议绑定/更新一次提交：先移除旧键，再按新 handler 做全局唯一检查，失败则回滚。

### B4. 设计期回调不能与引擎 `m_onClick` 双重绑定

引擎 MenuItem 点击时会同时触发 `m_onClick` 和 `SetCallback` 回调（`src/Menu.cpp` P0-98/P0-103）。设计器 `syncMenus` 只应使用 `SetCallback` 打点；**不要**在同一个设计期 MenuItem 上再 `setOnClick`。预览若由 LayoutParser 重建菜单，则只走 parser 的 `m_onClick`，不要再叠加设计器回调。另注意引擎菜单 click 是延迟一帧执行，`auto=2` 探针需在下一帧 `ProcessEvents` 后检查。

### B5. 菜单文本编辑导致绑定丢失

§6.2 的“路径不存在则丢弃 + 状态栏提示”可接受，但这是不可逆数据变更；请在应用菜单文本前明确提示（或先备份旧 `extended.menus`），并确保该操作进入撤销快照。不要用 caption 模糊迁移（设计已排除，正确）。

### B6. Schema/文档描述补齐

Schema 当前因 `menus.items` 宽松而接受 `events`，但描述未列出 `events.onClick`。建议引擎在 `docs/schema/declarative-ui.schema.json` 的 `menus` description 明确 `items[].events.onClick`，并在用户手册“事件/菜单”章节确认示例可运行；`validate_layout --strict` 保持通过。此项是文档/契约补齐，不改变运行时行为。

## 3. 设计待评审问题答复

1. **菜单树放 `evHost` 动态 TreeView**：可接受。属于设计器 UI，不影响引擎；注意 TreeView 滚动/空树提示。
2. **路径失配丢弃还是 caption 迁移**：按设计**丢弃并提示**；caption 可重名，不能作为迁移键。建议保留旧模型到撤销/提示，避免静默丢失。
3. **预览是否执行 handler**：V1 **不执行**可接受。引擎只有宿主先 `RegisterAction` 才会绑定；预览若未注册只会得到缺失 handler 诊断。若未来执行，需明确预览动作注册与生命周期。

## 4. 验收建议

- 设计器 auto=2 至少覆盖：无 id 菜单项 `events.onClick` 加载、绑定/更新/删除、separator 插入后的路径保持、保存/打开往返、导出 `event_list` 含菜单路径。
- auto=3 覆盖深层子菜单树显示与点击打点；strict 校验含菜单事件布局。
- 引擎侧无需新增测试；现有 `test_layout` / `layouts/test_layout.json` 已覆盖菜单事件解析，可作为回归基线。若实现 B2，需补同一 menu-bar 多项绑定的导出区分测试。

## 5. 放行意见

整体方案可行，引擎侧**不需要新增 C ABI/C++ Binding 或 LayoutParser 能力**。完成 B1~B6 的设计/文档修订后即可进入实施；B2/B3 属于设计器内部实现约束，B6 为引擎文档补齐。当前不建议直接实施，先按上述意见更新设计草案再复核。
