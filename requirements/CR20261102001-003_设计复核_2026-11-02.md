## 2. CR2002

### 阻塞：`padding` 属性键与既有 Dialog 冲突

- 引擎已有 `PropertyNames::kPadding = "padding"`，Dialog 以 **Float** 读写 `padding`（`setPadding(float)`，JSON 数字）；CR2002 又把 `padding` 定义为 **Margin/四边**（对象/字符串）。同一个属性键存在两种类型/语义。
- CR2002 §4.5/Q9 说“Dialog 复用现有 m_padding 语义”，但：
  - Dialog 是单 float（统一内缩），CR2002 是四边 Margin；
  - `SetString("padding","6 12")` 与 Dialog `SetFloat("padding",28)` 冲突；
  - schema `$defs/common.padding` 与 Dialog `padding` 类型冲突，严格校验会歧义；
  - 旧 Dialog JSON 的 `"padding": 28` 必须保持兼容，不能简单改成四边对象。
- 需定稿以下之一：
  1. 通用控件 padding 使用 **`content-padding`**（CSS `padding` 映射到它）；Dialog 保留 `padding` 数字；旧布局零变化；或
  2. Dialog 改用 `dialog-padding`，`padding` 作为通用四边，同时为旧 Dialog `padding` 数字提供兼容别名/迁移；或
  3. 明确按控件类型解释 `padding`（Dialog=float，其它=四边）并提供统一 C ABI；schema 需允许两型并文档说明。
- **建议**：优先方案 1（`content-padding`），语义最清晰、旧 Dialog 零风险；CSS 层仍叫 `padding`，设计器 UI 显示“内容内边距”。

### 其它需确认

- Q2 绝对布局：contentRect 只用于裁剪/可用区域，不移动子控件；请补“绝对布局子控件是否裁剪到 contentRect”的明确测试。
- Q6 Label `margin` 与 padding 叠加：确认保留双叠加是否会让旧 Label 文本偏移变化；需默认 padding=0 回归。
- Q9 Dialog：若采用独立 key，确认 Dialog 原有 `padding` API/JSON 完全不变；若统一，需迁移方案。
- `ListView/TreeView` 的 hitTest/GetNodeAt 扣除 padding 后与滚动条外缘一致。
