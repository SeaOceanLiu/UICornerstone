## 2. 总耗时拆解

| 阶段 | 耗时 |

| 主实例 Create | ~225ms |

## 3. LoadLayout 3.81s

引擎内部插桩（Release，单次运行）：

| 子阶段 | 耗时 |
|--------|------|
| `resourceProviders` 预扫描 JSON | ~1–2ms |
| LayoutParser JSON 解析 | **~1.3ms** |
| 控件树解析/构造 | **~2.9–3.2s** |
| 字体继承后处理 | ~0.20s |
| 主题应用（Layout 无 theme） | 0 |

控件构造样本：

- Label 总计约 40–54ms：构造约 10ms、旧主题字体/颜色约 10ms、通用属性约 10–21ms、其余 caption/布局约 10–12ms。
- Button 约 20–22ms；Combo/TextArea 约 79–88ms；ColorPicker 约 50ms；NumericUpDown 约 58ms。
- 大型容器/页签的耗时包含其子树，TabControl 约 1.77s，根 Panel 约 2.9s。

结论：**LoadLayout 的主要成本是每个控件的构造与属性写入/资源重建，不是 JSON 解析**。样本中单 Label 的不同阶段都出现约 10ms 的固定重建成本；`Label::setFont`/`setCaption` 等 setter 会触发 `recreate()`，布局解析期间同一控件被多次重建。

## 4. ApplyTheme 0.91s

引擎内部插桩：

| 子阶段 | 耗时 |
|--------|------|
| JSON 解析 + `setTheme` | <1ms |
| base 规则应用 | ~0.76–0.80s |
| variant | 0 |
| inheritPass | ~10ms |
| responsive（designer_theme 无 media/container） | 跳过 |

进一步拆解 `applyOne`：

- CSS 规则 `applyValue` 本身接近 0ms。
- **`replayExplicit` 占据绝大部分**：Label ~9.7ms、Button ~9.5ms、Combo/Edit ~19ms、ColorPicker ~29ms、MenuBar ~50ms。
- `main_layout.json` 中大量 Label 显式声明 `font {name,size}`；`replayExplicit` 重新调用 `applyFontToControl`，再次触发字体释放/重建。

结论：**ApplyTheme 的约 0.9s 不是主题规则匹配，也不是 JSON 解析，而是显式覆盖回放（尤其字体）导致重复资源重建**。

## 5. 是否需要替换 JSON / 预编译

**不需要为当前启动性能替换 JSON 或做布局预编译。**

- LayoutParser JSON 解析约 **1.3ms**，只占 LoadLayout 的 0.04% 左右；Python 基线也仅约 2.25ms。
- 主题 JSON 仅 3.5KB，解析/setTheme <1ms。
- 即使把 JSON 解析优化到 0，也只能节省毫秒级，无法解决 3–4 秒的控件构造和 0.8 秒的显式回放。
- 真正有价值的方向是：
  1. 布局解析期间批量写属性、抑制逐 setter `recreate()`，最后统一 create/reflow；
  2. 同一字体/字号/样式共享字体资源，`setFont` 值未变化时跳过 `releaseFont`/recreate；
  3. `replayExplicit` 写入前比较当前值，跳过未变化属性（尤其 font/font-size）；
  4. 主题应用把 base 值、显式回放和 inherit 合成一次遍历，批量刷新；
  5. 若未来布局规模增长到 JSON 解析成为可观成本，再考虑二进制布局缓存；当前 148 个 JSON 控件、145KB 规模没有收益。

## 6. 建议的后续优化优先级

1. **字体资源重建消除**（LoadLayout + ApplyTheme 共同收益，最高）。
2. **布局解析两阶段化**：先解析完整属性，后一次 create/reflow（消除约 40ms/Label 的重复成本）。
3. **ApplyTheme 显式回放去重**（当前约 0.76s 可大幅下降）。
4. **控件类型构造优化**（Combo/Edit/TextArea 等约 80ms）。
5. JSON/预编译仅作为大数据量布局的远期选项。
