## 1. 补充 1：载荷捕获时机与 drag-accept 重置语义（建议在设计中写明）

- **载荷在拖动启动时捕获**（命中元素：tree 节点/list 行/tab 页）并在整个拖动期间**不变**——避免落下时重新命中导致"源变了"；
- `drag-accept` 建议语义：**进入新目标或落点变化时重置为默认（接受）**，`drop` 读取最后一次设定值；跨目标切换不残留上一目标的拒绝态。

## 2. 补充 2：MoveNode/MoveRow 建议直接作为公开 API

Phase 2 的两个 helper（tree 换序/换父、list 行换序）建议**同时公开**（Binding/C ABI），理由：设计器后续"控件树拖动换父/换序、结构行拖动编辑"（Phase 3）以及宿主的自实现换序都直接需要；引擎内部行为复用同一实现即可。

## 3. 补充 3：Q-3 的 userData 责任边界注明

`id/text` 引擎缓冲（回调期有效 ✓）；`userData` 为**宿主指针透传**——建议文档明确"引擎不校验/不持有其生命周期，宿主保证回调期有效"。

## 4. 补充 4：只读查询建议

`drag-active` ✓（确认）；可选补只读 `drag-hint`（当前落点快照）——宿主轮询即可做自绘预览（Phase 3 的自绘能力前置）。

## 6. 关于"是否一次让引擎完成 Phase 1~3"的答复（设计器侧意见）

**Phase 3 不可能由引擎代做**——其内容（控件树拖动换父/换序、画布内控件拖动迁移到统一通道、结构行拖动编辑）全部是**设计器侧的编辑语义**（模型/撤销/树同步/宿主状态），引擎无从实施 ✗。所以问题实际是"Phase 1+2 是否合并一批"：

**建议：Phase 1+2 合并一批（倾向）**，理由：
1. Phase 2 是同一状态机/事件面的**三个内置消费者**（tree/list/tab），不引入新架构面；合并只扩大测试面、不扩大设计面；
2. **P0-93（运行时页签排序）随之立即闭环**——用户实际最想用的是导出应用的拖拽能力；少一轮"实施→同步→联测"周期；
3. 引擎测试计划（§5）已覆盖 Phase 1/2 探针，合并后一次跑齐。

**可接受的替代**：若引擎对框架 ABI 稳定性有顾虑（设计 Q-1 的独立批次理由），Phase 1 单独先行亦可——与我们既有批次节奏一致，Phase 2 紧随。**不建议**把 Phase 2 再拆成三次（tree/list/tab 分开）——同一机制的三个消费者拆批没有收益。

**设计器侧随批计划**（无论怎么分批）：Phase 1 交付后先做**只读验证**（探针：注册/阈值/载荷/跨子视口/Esc）；Phase 2 交付后做**页签内置排序联测**（`reorderable` 行 + 导出携带 + 与现有宿主拖动并存/切换评估）；Phase 3 由设计器按批实施。
